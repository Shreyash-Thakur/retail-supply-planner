# Design decisions

One entry per phase. Spec amendments agreed with the author are listed at the top of `docs/BUILD_PLAN.md`; each is explained here in the phase that builds it.

## Phase 0: Setup
What was built: the project skeleton (config, error type, stage runner with placeholder stages, placeholder dashboard, README with data download steps) and a Python 3.12 virtual environment with every dependency installed.
Key decision: Python 3.12 instead of the spec's 3.11 (amendment 1); config paths resolve against the project root; a `pytest.ini` sets `pythonpath = .`.
Why: 3.11 was not installed and every dependency ships stable 3.12 wheels, including LightGBM on native Windows, so no WSL is needed. Resolving paths against the project root means `run_all.py`, the tests and the app behave the same from any working directory. Without `pythonpath = .`, pytest cannot import `src` from the `tests` folder.
Numbers: installed versions: pandas 3.0.6, numpy 2.5.4, pyarrow 26.0.0, duckdb 1.5.6, statsmodels 0.15.0, lightgbm 4.7.0, scipy 1.18.1, pyyaml 6.0.3, streamlit 1.66.0, plotly 7.1.0, pytest 9.1.1. LightGBM native `lgb.train` with a Tweedie objective runs on native Windows. `pytest -q`: 2 passed.

## Phase 1: Medallion pipeline
What was built: a DuckDB pipeline that converts the three M5 CSVs to bronze parquet, selects a 150-item FOODS_3 slice, unpivots it to 2.9 million daily rows (silver), and aggregates to one weekly row per item and DC (gold) with calendar, SNAP and price features. Quality checks raise `DataQualityError` on nulls, negative units, duplicate keys, gaps after launch, missing prices, or wrong DC and item counts.
Key decisions:
- Slice before reshaping: rank FOODS_3 items on the wide table, then unpivot only the 150 chosen items, so the long table has 2.9 million rows instead of 59.2 million (30,490 series x 1,941 days) for the whole dataset.
- Slice volume window ends at fold 1's origin (amendment 2): the top 100 items by units over t 189 to 240 (weeks 11433 to 11532), plus 50 random extras from the other 723 items with the seeded generator. Ties are broken by item_id.
- Drop the partial last week: week 11617 has only 2 of its 7 days in the sales data.
- Pre-launch weeks are kept in gold but flagged `is_launched = False`; zero weeks after launch are real zeros and stay.
- DC weekly price is the mean of the distinct store-week prices, so each store counts once regardless of how many days it has. Pre-launch rows keep their observed price (M5 has none there) and are never filled.
- Price fill order for launched rows: forward-fill, then back-fill, then the item's median price across DCs, with counts logged for each step.
Why: reshaping all 30,490 series first is what causes memory errors. Ranking items on the last 52 weeks would pick items that happened to sell well in the very weeks we test on, which inflates backtest scores (selection bias); ranking on the 52 weeks before the first test window avoids that. A partial week looks like a sales drop and would distort models, metrics and segments. Weeks before an item is stocked are not zero demand: counting them as zeros would make items look intermittent and drag forecasts down. Averaging daily rows would weight stores by days; averaging store-weeks gives each store equal weight.
Numbers (from `python run_all.py --stage pipeline`): 150 items (100 top_volume, 50 random_extra), 3 DCs, 277 weeks (t 0 to 276, weeks 11101 to 11616), 2,911,500 silver rows, 124,650 gold rows (109,368 launched, 15,282 pre-launch), dropped week 11617 (2 days), 0 never-launched series, 0 launched rows missing a price (M5 prices every store-week in which an item sells), 8,100 launched zero-sales weeks kept. Gold units per DC match the raw CSV exactly (CA 7,617,313; TX 5,878,140; WI 5,089,205). Runtime 10.3 s. A second run gives identical slice and gold files.

## Phase 2: Simulated supply parameters
What was built: per item and DC, mean weekly demand, opening stock and DC capacity; per item, lead time, weekly supplier capacity, unit price, unit cost and weekly holding cost. All supply values are simulated from the real demand history, because M5 contains sales only.
Key decisions:
- Every parameter uses the last 52 launched weeks up to `T_last` (`supply.history_weeks`, added to config so the number is not hidden in code). These parameters feed only the forward simulation after `T_last`, never a backtest, so using the latest weeks is not leakage.
- Lead time is drawn once per item (uniform 1 to 4 weeks, seeded) and shared by all three DCs, because one supplier ships the item to every DC.
- Supplier capacity is 1.10 x the item's mean weekly demand summed over DCs: about 10% headroom on average, so capacity can bind when demand spikes or several DCs reorder in the same week, which is the situation the LP allocation is for (Phase 7 measures how often it does).
- Capacities are rounded up to whole units after rounding to 9 decimals, because floating point turns 1.1 x 50 into 55.00000000000001, which a plain ceiling would push to 56. A test covers this exact case.
- DC capacity is stored as a column on `supply_params.parquet` (one value per DC, repeated per item), since the spec names only two output files.
- Opening stock uses numpy rounding (round half to even); the difference from round half up is at most one unit on a tie.
Why: a planner needs supply constraints to make allocation and safety stock meaningful, and M5 has none. Deriving them from each series' own demand keeps them realistic in scale, and the fixed seed makes every run reproducible.
Numbers (from `python run_all.py --stage supply`): 450 series, 150 items, 0 series with fewer than 52 launched weeks, 0 floored at 1 unit. Lead times: 1 week 35 items, 2 weeks 36, 3 weeks 38, 4 weeks 41. Total supplier capacity 75,013 units per week against 68,129.6 units mean weekly demand. DC capacities: CA 221,380, TX 163,794, WI 159,864 units. Total opening stock 204,395 units. Unit price median 1.97, range 0.20 to 10.84. Two runs give byte-identical files.

## Phase 3: Segmentation
What was built: ABC (revenue), XYZ (coefficient of variation) and Syntetos-Boylan demand pattern (ADI and CV squared) for every item and DC, computed by a function `segment(weekly, origin, cfg)` that sees only launched weeks up to the origin. One segment set is stored per backtest fold origin (t 240, 252, 264) plus a `final` set at `T_last` (t 276).
Key decisions:
- Segments per fold (amendment 4): each fold's LightGBM features, model selection grouping and evaluation use the segment set computed at that fold's origin; the final forecast, inventory, allocation and simulation use the `final` set. A test changes every unit and price after the origin and asserts the segments do not change.
- ABC boundary rule (amendment 3): a series is A if the cumulative revenue share before adding it is below 0.80, B if below 0.95, else C. The series that pushes the share past 80% is still one of the biggest earners, so it stays A, and the top series is always A.
- Standard deviations are population (ddof 0), so a constant series has cv 0 and a single non-zero week gives cv2 0, as the spec requires. A series with zero mean is Z and its cv is left empty.
- Window: the last 52 launched weeks up to the origin. Pre-launch weeks are excluded, so a new item is not classed intermittent just because it was not yet stocked.
Why: using segments computed from weeks after a fold's origin would leak test information into features and model choice and quietly flatter the backtest. ABC drives service levels and allocation weights; XYZ shows how hard a series is to forecast; the demand pattern decides which model family suits it (smoothing methods for smooth demand, Croston or TSB for intermittent demand).
Numbers (from `python run_all.py --stage segment`): final set: ABC A 166, B 132, C 152 series, with revenue shares 0.801, 0.149, 0.049. XYZ X 297, Y 125, Z 28. Patterns: smooth 378, erratic 7, intermittent 61, lumpy 4, inactive 0. ABC by XYZ: A 129/34/3, B 83/39/10, C 85/52/15. Pattern counts per fold: fold_1 379/15/45/11/0, fold_2 381/7/53/7/2, fold_3 369/9/66/6/0 (smooth/erratic/intermittent/lumpy/inactive). Share of series whose pattern differs from the final set: fold_1 12.7%, fold_2 7.3%, fold_3 4.7%, which is the drift the per-fold rule protects against. Erratic and lumpy groups are small (4 to 15 series), so their model choice in Phase 5 rests on few series.

## Phase 4: Forecasting models
What was built: seven forecasters behind one interface, `forecast(history, future, horizon, cfg)`, returning item_id, dc_id, t, h, model, forecast and fallback: naive, seasonal naive, 4-week moving average, Holt-Winters (with simple exponential smoothing and seasonal naive fallbacks), Croston, TSB, and LightGBM (Tweedie point models plus quantile models). Every output is clipped at 0 and never NaN: a missing or non-finite value falls back to naive and is flagged.
Key decisions:
- Direct, horizon-grouped LightGBM: three models, for h 1 to 4, 5 to 8 and 9 to 12 (`forecast.horizon_groups` in config). For the group whose largest horizon is L, every lag and rolling feature for target week t uses week t - L or earlier (lags L, L+1, L+2, L+4 and 52; rolling mean and std over 4, 8, 13 and 26 weeks of the series shifted by L). Since h <= L, t - L <= origin, so every feature is known at the origin. A test sets units equal to t and asserts no feature for any target week exceeds the origin; another passes fake future units and asserts the features do not change.
- `h` is not used as a feature, although the spec lists it. With target-relative lags, a target week's feature row is identical for every h in its group, so h carries no information a model could learn from; including it would mean replicating each training row four times for nothing. Each group's model already is the horizon-specific part.
- Future rows enter the feature panel with units set to missing, so leakage is impossible by construction rather than by care. Price at the target week is used as the planned price (known in advance); its ratio to the series' median price uses the median of history up to the origin only.
- Tweedie objective (power 1.2) for the point models: weekly item sales are counts with many zeros and a long right tail, which squared error handles badly and Tweedie models directly.
- Early stopping on the last 12 weeks before the origin, then a refit on all training rows with the best iteration, so the most recent weeks are not lost to validation. Training rows need every lag feature present, which means 52 weeks plus the lag before a series contributes.
- Quantile models (0.5, 0.9, 0.95, 0.98) are trained only for the final forecast, where safety stock and the dashboard need them; the backtest scores point forecasts, so training 12 extra models per fold would cost time for nothing. Quantiles are sorted per row so they never cross.
- Croston initialises z at the first non-zero demand and p at its 1-based position, and updates only on non-zero weeks; TSB updates the demand probability every week, so it decays toward 0 when an item stops selling. Tests check Croston on [0,0,3,0,0,3,0,0,3] gives exactly 1.0 and that TSB falls but Croston does not after 20 trailing zeros.
- Holt-Winters fits run in a pool of 6 processes with one BLAS thread each (`forecast.stat_workers`). The first attempt used one process per CPU and ran out of memory (20 CPUs x 20 OpenBLAS threads each); see the local error notes.
Why: one interface lets the backtest treat every model the same way and makes fallbacks visible. Direct models avoid the error build-up of feeding forecasts back in as lags, and the lag rule makes leakage-freedom something a test can prove.
Numbers (Phase 4 acceptance check from fold 1's origin, t 240, 450 series x 12 weeks = 5,400 rows per model): every model returned 5,400 rows covering all 450 series and h 1 to 12, with 0 NaN, 0 negative values and 0 fallback series. Holt-Winters used the seasonal model for 426 series and simple exponential smoothing for 24 (fewer than 104 launched weeks). LightGBM: 69,768 training rows per group, best iterations 522, 331 and 428. Runtimes: Holt-Winters 28.1 s, LightGBM 41.0 s, the others under 0.2 s. This is a single-fold check; the scored comparison is Phase 5.

## Phase 5: Backtesting and model selection
What was built: a rolling-origin backtest over three non-overlapping 12-week folds (origins t 240, 252 and 264), in which every model trains only on weeks up to the origin, plus volume-weighted scoring (WAPE, bias, mean MASE, FVA vs naive) by model, demand pattern and ABC class, a model choice per pattern, and the residuals of each series' chosen model for safety stock and simulation.
Key decisions:
- WAPE over MAPE: MAPE divides by each week's actual, so it explodes or is undefined on the many zero and low-sales weeks in this data, and it treats an error on a 2-unit item like one on a 2,000-unit item. WAPE weights errors by volume, which is what drives stock and cost.
- Volume-weighted aggregation: WAPE and bias are computed on pooled absolute errors and pooled actuals, never as an average of per-series WAPEs, so small noisy series cannot dominate the score. A test shows the two give different answers.
- FVA vs naive: forecast value added is the naive WAPE minus the model WAPE in percentage points. If a model cannot beat "same as last week" it is not adding value, however sophisticated it is.
- Patterns per fold (amendment 4): each forecast row is grouped by the series' pattern in its own fold's segment set, so a series can count as smooth in one fold and intermittent in another.
- Model selection per pattern, not per item: with only 3 folds of 12 weeks, choosing a model per series would mostly pick whichever model got lucky on that series' noise (overfitting the backtest). Pooling all series with the same pattern gives hundreds of series-folds per choice for the main patterns.
- The selection rule was applied exactly as specified (lowest pooled WAPE, tie-break by absolute bias, inactive always TSB), even where the result is debatable (see below), so it can be explained without hand-tuning.
- Residuals for safety stock and simulation are actual minus forecast of the model each series will use in the final forecast, which is the model chosen for its final-set pattern, across all three folds (450 series x 3 folds x 12 horizons).
Why: honest out-of-sample numbers are the only defensible basis for choosing models, setting safety stock from forecast error and claiming value added.
Numbers (from `python run_all.py --stage backtest`, runtime 128.3 s): overall WAPE: lightgbm 0.280 (bias -5.8%, mean MASE 0.619, FVA +8.9 pp), tsb 0.333, croston 0.345, moving_average_4 0.348, holt_winters 0.365, naive 0.369, seasonal_naive 0.382 (FVA -1.3 pp). LightGBM WAPE per fold 0.275, 0.307, 0.261 against naive 0.458, 0.378, 0.278. By ABC, LightGBM WAPE is A 0.239, B 0.337, C 0.418. Selected models: smooth lightgbm (WAPE 0.242, 1,129 series-folds, 4.3 pp ahead of tsb); erratic lightgbm (0.547, 31 series-folds, 21.4 pp ahead of seasonal_naive); intermittent naive (0.744, 164 series-folds, only 0.2 pp ahead of lightgbm 0.746); lumpy lightgbm (0.913, 24 series-folds); inactive tsb by rule (2 series-folds; croston scored lower there, a sample too small to override the rule). 0 fallback rows in 113,400 forecasts.
Caveat on intermittent: naive wins by 0.2 pp with a -17.3% bias. For intermittent series naive forecasts zero in 49.4% of weeks while only 36.7% of actual weeks are zero. WAPE is minimised by forecasting the median, which for intermittent demand is often zero, so it rewards under-forecasting. The rule picks naive; safety stock from the larger residuals has to cover the gap, and the simulation in Phase 8 will show whether service suffers for these series. A selection rule that prefers the lower absolute bias within a small WAPE margin would pick lightgbm here; that would be a change to the agreed rule, so it is noted rather than made.

## Phase 6: Final forecast and inventory policy
What was built: the `forecast` stage forecasts the 12 weeks after `T_last` (weeks 11617 to 11628) with the model chosen for each series' final-set pattern, plus LightGBM quantile forecasts (q50, q90, q95, q98) for every series; the `inventory` stage turns them into a policy per item and DC: safety stock (classic and quantile), lead-time demand, reorder point, order-up-to level and days of cover. The final forecast lives in a new module, `src/final_forecast.py`, because it needs the backtest's model registry and the calendar fill, and fits neither `backtest.py` nor `inventory.py`.
Key decisions:
- Calendar gap (amendment 5): calendar.csv ends at d_1969, so 54 of the 84 future days (5 days of week 11621 and all of weeks 11622 to 11628) are filled by date and flagged `calendar_estimated`: SNAP from each state's day-of-month schedule (identical in all 64 complete months, asserted in code, raising if it ever differs), events from the same month and day a year earlier. A test checks that July 4 is copied and SNAP days follow the schedule.
- Prices are held flat at each series' last launched price for the whole horizon, because planned prices beyond the data are unknown.
- Classic safety stock = z x sigma_e x sqrt(L), with z from the cycle service level of the series' ABC class (A 0.98, B 0.95, C 0.90) and sigma_e the standard deviation of the chosen model's backtest errors at horizons 1 to 4 (12 errors per series from 3 folds; every series had at least 6, so none fell back to demand std). Safety stock comes from forecast error, not demand variability, because the error is what the stock has to absorb: a perfectly forecast seasonal item needs no buffer for its swings.
- Quantile safety stock = sqrt(sum over the L lead-time weeks of (q_high - q50)^2). Weekly quantiles cannot be added (the sum of weekly 95th percentiles is far above the 95th percentile of the total), so each week's band is treated as an independent error and the bands are added in quadrature. The independence assumption understates risk if errors are correlated week to week.
- The policy uses classic safety stock (`inventory.safety_stock_method: classic`), which is simpler to explain and audit; the quantile version is reported alongside.
- Order-up-to = reorder point + the forecast for week L + 1 (one-week review period). Days of cover = opening stock / (mean weekly forecast / 7), left empty when the forecast is zero.
- Cycle service level vs fill rate: the 0.98 for A items is the probability of not stocking out in a replenishment cycle, not the share of demand served; the simulation reports both.
- ABC-differentiated service levels: A items carry 80% of revenue, so the extra stock to protect them pays for itself; holding C items at 0.98 too would add inventory for little revenue (Phase 8 tests this as the flat_service_level scenario).
Why: the policy has to rest on measured forecast error from honest backtests, with every assumption (flat prices, independent weekly errors, estimated calendar) written down.
Numbers (from `python run_all.py --stage forecast` and `--stage inventory`): 450 series x 12 weeks, 0 fallback rows; 389 series use lightgbm and 61 naive (the intermittent choice). Total forecast 883,874 units over 12 weeks (q50 894,043, q95 1,342,223), about 73,700 per week against 69,748 per week actual over the last 12 weeks. LightGBM final models trained on 85,968 rows per group, best iterations 113, 119, 134. Mean safety stock (classic / quantile): A 247.2 / 245.8, B 82.1 / 115.7, C 44.4 / 47.9 units; total 58,608 classic vs 63,358 quantile. Mean reorder point A 1,063.4, B 297.6, C 161.6. Median days of cover A 19.6, B 18.8, C 18.7.
Consequence of the intermittent rule: 21 series (14 B, 7 C), all intermittent and assigned naive, had zero sales in their last week, so their whole 12-week forecast is 0 although their recent mean demand is 92 units per week (16 to 166). Their order-up-to level is safety stock alone (110 units on average). This follows the agreed selection rule and is kept; Phase 8 measures what it costs.

## Phase 7: Allocation of constrained supply
What was built: `allocate_lp`, a linear program (scipy HiGHS) that splits each item's limited supplier capacity across the three DCs to maximise weighted shipments, subject to each DC's request, each item's supply and each DC's free capacity; `allocate_fair_share`, the baseline that gives every DC the same share of its request; integer rounding that never breaks a constraint; and a printed demo of one constrained week.
Key decisions:
- LP weights w = abc_weight x (1 + 1 / (1 + weeks of cover)), with ABC weights A 3, B 2, C 1. The class term protects revenue; the cover term sends units to the DC closest to stocking out, so between two DCs of the same class the emptier one wins. Weeks of cover = on hand / mean weekly forecast.
- When nothing binds (every item's supply and every DC's free capacity cover the requests), the LP is skipped and every request is filled, which is exactly the LP optimum because all weights are positive. This keeps the simulation fast without changing any result.
- The constraint matrix is a bipartite incidence structure (items by DCs) with whole-unit bounds, which is totally unimodular, so HiGHS returns whole-unit vertex solutions; the round-down-then-hand-out step is a safety net for any fractional result and is tested against every constraint on 50 random cases.
- If the solver fails, that week falls back to fair share and the failure is logged.
- The demo needs a week in which supply actually binds. In normal running the opening stock and pipeline cover most requests, so the demo uses a stated stress setting: each DC holds its opening stock, nothing is in transit (as after a supply interruption), and supplier capacity is at the supplier_disruption level (50%).
Why: when supply is short, an equal split ignores which shortages cost more. The LP makes the trade-off explicit and auditable: every unit goes where the weight, meaning revenue class and stockout urgency, is highest.
Numbers (from `python run_all.py --stage inventory`): 122,065 units requested against 37,466 units of supply; 105 of 150 items constrained. Both methods ship 28,435 units (the rest of the supply belongs to items whose requests are below capacity). Fill of requests by class: LP A 25.7%, B 16.7%, C 15.4%; fair share A 23.7%, B 22.1%, C 22.0%. Weighted shortfall: LP 317,784 vs fair share 321,704, 1.2% lower. The gain is modest because capacity is per item: the LP can only move an item's units between its own DCs (the same item can be A in one DC and B in another). Items compete with each other only through DC capacity, which is 8 weeks of demand and does not bind here.

## Phase 8: Monte Carlo simulation and scenarios
What was built: a vectorised 12-week simulation of all 450 series over 200 runs. Each week it receives arrivals, meets demand from stock (unmet demand is lost), orders up to the policy level, allocates limited supplier capacity across DCs (LP or fair share) and ships with the item's lead time, asserting stock balance every week. It covers 7 scenarios plus one labelled diagnostic, with KPIs overall, by ABC class and by chosen model.
Key decisions:
- Lost sales, no backorders: a shopper who finds the shelf empty buys another brand, which is the usual case in grocery and FMCG. A test checks that demand does not grow after stockouts.
- Demand = max(0, round(forecast + residual)), with residuals drawn from the series' own backtest errors for the matching horizon group (all 1,350 series-groups had at least 10, so the pooled-pattern fallback, which is implemented and tested, was not needed).
- Common random numbers: every scenario uses the same 200 demand paths, so a difference between scenarios comes from the scenario, not from sampling luck. The p10 to p90 fill-rate bands are under 1 point wide.
- Weeks of cover in the allocation weights uses the inventory position (on hand plus in transit), not on hand alone (`allocation.cover_basis: position`): a unit shipped today joins the position and arrives L weeks later, so urgency measured on today's shelf alone is stale. Decided on that reasoning; both were run and reported: on-hand cover gave LP fill 0.9210, position cover 0.9235.
- When no DC's capacity binds, allocation uses the exact per-item greedy solution instead of calling the solver (same optimum, tested against the LP on 50 random cases), so the run takes 8 seconds rather than minutes.
- Added a diagnostic scenario with effectively unlimited supplier capacity. It is not one of the spec's scenarios; it separates the policy's own performance from the effect of the capacity limit.
- The lead time shock adds 2 weeks to new orders only (stock already in transit keeps its arrival week), and is run twice: with the original policy and with the policy recomputed for the longer lead time.
Why: the policy and allocation rules are only as good as their behaviour under uncertainty; the simulation measures fill rate and cost directly instead of trusting the service-level formula.
Numbers (from `python run_all.py --stage simulate`, 200 runs x 12 weeks, total runtime 8.0 s; means across runs):
- Baseline (LP): fill rate 0.924 (p10 to p90: 0.919 to 0.927), cycle service 0.885, 1.38 stockout weeks per series, average inventory value 140,206, holding cost 8,089, lost sales value 201,771. Fill by class: A 0.937, B 0.900, C 0.877.
- Supplier capacity binds in 59.4% of item-weeks: capacity is 1.10 x the 52-week mean demand, but the summer forecast runs about 8% above that mean. With unlimited supply the same policy reaches fill 0.994 and lost sales value 15,121, so most lost sales come from capacity, not from the safety stock formula.
- Fair share beats the LP on fill rate in every class (all 0.938 vs 0.924; A 0.942 vs 0.937) with less inventory (134,146 vs 140,206) and lower lost sales value (176,876 vs 201,771). The LP wins on its own objective (the one-week demo: 1.2% lower weighted shortfall), but that objective rewards weighted units shipped, and a linear objective allocates all or nothing: it fills the top-weight DC's whole request, safety stock included, before the next DC gets any. The loss is concentrated in items whose three DCs are all class A, where only the cover term separates them (341,931 extra lost units over 50 diagnostic runs, measured with on-hand cover). Hedging across DCs, which fair share does implicitly, is worth more here than the LP's priority ordering. A formulation that values units covering expected demand above units topping up safety stock would address this; it is a change to the specified objective and is left as a proposal.
- Demand surge (A items in CA +25% for weeks 2 to 5): fill 0.914, lost sales value 224,473.
- Supplier disruption (capacity 50% for weeks 3 to 5): fill 0.845, 2.59 stockout weeks per series, lost sales value 343,640.
- Lead time shock (+2 weeks): with the policy not updated, fill 0.794 and average inventory falls to 77,189 units as the pipeline empties; with the policy updated, fill 0.865. Recomputing reorder points for the new lead time recovers 7.1 points of fill.
- Flat 0.98 service level for every series: fill 0.925 vs 0.924, inventory value 141,889 vs 140,206 (+1.2%). Differentiating by ABC class costs almost nothing in fill, partly because extra safety stock cannot be filled while supply binds.
- Series on naive forecasts (the intermittent choice): fill 0.651 in the baseline, against 0.950 for series on LightGBM. This is the cost of the selection rule's 0.2-point WAPE preference for naive on intermittent series noted in Phase 5.
- Addendum from the dashboard review: baseline weekly fill rate falls steadily from about 99% in week 1 to about 86% in week 12. The run starts with more stock than the policy targets (opening stock plus pipeline 384,839 units against order-up-to levels of 313,611), and that buffer runs down because supplier capacity binds in most item-weeks, so the 12-week average of 92.4% is not a steady state.

## Phase 9: Dashboard, docs and results
What was built: the `app_data` stage writes 13 small files (2.7 MB) for the dashboard and regenerates RESULTS.md from the run outputs; a seven-page Streamlit dashboard (overview, segmentation, forecast accuracy, item explorer, inventory policy, allocation, scenarios) reads only `app_data/`; README with a stage diagram, run instructions and limitations.
Key decisions:
- RESULTS.md is generated from `data/outputs/` by code, with the producing stage command named above each block, so its numbers cannot drift from the files. A fresh copy of the repository plus the raw CSVs, run with `python run_all.py --stage all`, reproduced every output file and RESULTS.md exactly.
- `app_data/` is gitignored until the author confirms the M5 data rules allow publishing derived results (the decision reserved for the author in Phase 9a); deployment waits for the same decision.
- Charts use three validated categorical colours (blue, orange, aqua, checked with the colour-vision validator) fixed to entities, so class A, the LP or the baseline keep their colour on every page; the aqua is below 3:1 contrast on a light background, so every chart carries direct value labels or a table. WAPE heatmaps cap the colour scale at 1.0 so the lumpy group's large errors do not flatten the rest; printed values stay exact.
- Pages accept a `?page=` link (for example `?page=Scenarios`) for sharing and for screenshots.
Why: the dashboard is how a planner or interviewer meets the work, so it shows the same numbers as RESULTS.md, explains the counter-intuitive findings (fair share beating the LP, naive on intermittent series) where they appear, and says plainly which inputs are simulated.
Numbers: `python run_all.py --stage all` from scratch: 188 s, exit 0. App: every page renders without errors and the first page loads in 1.2 s. `pytest -q`: 72 passed.

## Phase 10 (stretch): Planner exceptions
What was built: an `exceptions` stage (between `simulate` and `app_data`) that lists every series needing attention, ranked by value at risk, with an Exceptions page in the dashboard. Four checks: stockout risk, overstock, forecast bias and demand anomaly; thresholds live in config (`exceptions` section).
Key decisions:
- Stockout risk uses a deterministic projection: the simulation's own weekly loop run once with expected demand (no noise), baseline supplier capacity and LP allocation, so the projection obeys exactly the same rules as the Monte Carlo runs. Flagged when projected on hand falls below safety stock in weeks 1 to 4; value at risk = projected lost units in those weeks x price.
- Overstock: days of cover above 60; excess = opening stock minus 60 days of forecast demand, valued at unit cost. A series holding stock with a zero forecast has unlimited cover and is flagged too.
- Forecast bias: the chosen model's bias over the last backtest fold beyond plus or minus 20%; value at risk = the absolute 12-week bias in units x price (the spec gives no value for this type, and this puts it in the same currency as the others).
- Demand anomaly: the last actual week compared with the last fold's forecast for that week plus the 5th and 95th percentiles of the series' backtest residuals; value at risk = the distance outside that range x price.
Why: a planner cannot review 450 series every week. Ranking by money at risk puts the few that matter first, and each row says why it was flagged.
Numbers (from `python run_all.py --stage exceptions`): 310 exceptions on 226 of 450 series. Forecast bias 180 (value at risk 216,611; 91 over-forecast, 89 under-forecast), stockout risk 58 (27,322), overstock 23 (4,412), demand anomaly 49 (2,207). The list independently surfaces the intermittent-naive problem from Phase 5: 21 of the 23 overstock flags are series whose naive forecast is zero, and naive series account for 31 of the 58 stockout risks although they are 61 of 450 series. The second-ranked exception is FOODS_3_444 in WI: forecast zero, projected to run out in week 1, 1,748 units lost in weeks 1 to 4.

## Phase 11 (stretch): Price elasticity and a price-cut scenario
What was built: an `elasticity` stage (before `simulate`) that estimates each item's own-price elasticity, pooled across DCs, by OLS of log(units) on log(price) with DC and month indicators, event days and SNAP days, on launched weeks with sales; and two price-cut scenarios in the simulation, with a revenue KPI added to every scenario.
Key decisions:
- Items need at least 3 distinct prices and a price coefficient of variation above 2%; otherwise `insufficient_variation` and the department mean (mean of the valid raw estimates) is used. Items whose price effect is not identified (price collinear with the controls) would be marked `not_identified`; none were.
- Shrinkage toward the department mean with weight n / (n + 20), n = number of weeks, then clipping to [-4, 0]; raw positive estimates are flagged.
- A sensitivity estimate with a linear time trend is stored next to the spec's estimate but not used, to test whether price drift over the years explains the wrong-signed estimates.
- The price cut is 10% on the 10 items with the most revenue (`scenarios.price_cut` in config); demand for them is multiplied by 0.9 ^ elasticity and revenue and lost sales are valued at the cut price. It runs twice, like the lead time shock: with the policy left as is (an unplanned promotion) and with the forecast, quantiles and order-up-to levels raised by the expected uplift (a planned one).
Why: price is the lever a planner is most often asked about, and a what-if is only credible if the elasticity behind it is shown with its uncertainty.
Numbers (from `python run_all.py --stage elasticity` and `--stage simulate`): 150 items; 108 with enough price variation, 42 insufficient. Raw estimates for the 108: median -0.629, 10th to 90th percentile -3.688 to 3.912, and 40 have the wrong (positive) sign; 75% have |t| > 2, so they are precisely estimated but often wrong, the signature of confounding rather than noise. Adding a time trend does not help (43 positive), so the problem is not just inflation. The likely cause, not tested here, is that in observational retail data prices move for reasons tied to demand (for example promotions timed to slow weeks, or increases on items that sell well), which biases a simple regression. The department mean is only -0.111, so the final elasticities are mild (median -0.111, mean -0.829 after clipping 51 items). Demand multipliers for the 10 cut items range from 1.000 to 1.304; only 4 exceed 1/0.9 = 1.111, the uplift needed to keep revenue flat. Result: revenue falls from 1,700,850 to 1,670,210 with the policy not updated and to 1,678,170 with it updated; fill rate falls from 0.924 to 0.909 and 0.914, because supplier capacity, already binding in 59% of item-weeks, cannot serve the extra demand. Planning for the promotion recovers 0.5 points of fill and 7,960 of revenue. Treat these elasticities as illustrative: a causal estimate would need price experiments or instruments.

## Phase 12 (stretch): Hierarchical consistency
What was built: a `hierarchy` stage that scores bottom-up and top-down forecasts on the last backtest fold (fold_3, origin t 264) at four levels: item-DC, item, DC and total.
Key decisions:
- Bottom-up: each series' backtest forecast from the model chosen for its fold_3 pattern, summed to each level.
- Top-down: the total series is forecast with a model chosen by backtesting the univariate candidates on the total over fold_1 and fold_2 only, so fold_3 stays unseen; the total forecast is split to item-DC by each series' share of units in the 52 weeks up to the origin, then summed to each level. LightGBM is not a candidate for the total: it learns across many series, and a single aggregate series of 265 weeks gives it nothing to pool.
- Caveat: the per-pattern model choice used for bottom-up was made on all three folds, fold_3 included, which gives bottom-up a small home advantage in this comparison.
Why: plans are made at several levels (DC capacity, supplier orders, item assortments), and the levels must add up. Which way to build them is an empirical question for each dataset.
Numbers (from `python run_all.py --stage hierarchy`): total-series model chosen on the earlier folds: seasonal_naive (WAPE 0.057, ahead of moving_average_4 0.089 and holt_winters 0.096). WAPE bottom-up vs top-down: item-DC 0.258 vs 0.316, item 0.207 vs 0.274, DC 0.055 vs 0.105, total 0.040 vs 0.102. Bottom-up wins at every level, the total included: series-level errors partly cancel when summed, while the top-down total rests on one univariate model and fixed historical shares, so it cannot see item-level shifts such as an item gaining or losing share. The home-advantage caveat is far smaller than a 6-point gap at the total.

## Amendment 9: bias tie-break in model selection
What was built: model selection now chooses, per pattern, the model with the lowest absolute bias among those within 1.0 WAPE point of the lowest WAPE (`forecast.selection_wape_margin_pp`); a margin of 0 gives back the original rule, and tests cover both. Every stage from `backtest` on was rerun.
Key decision: treat models whose WAPE differs by less than a point as tied, and break the tie on bias, because a planner can absorb a slightly noisier forecast with safety stock but a forecast that is persistently too low starves the shelf. Agreed with the author after the first full run.
Why: the original rule chose naive for intermittent series by 0.2 points of WAPE while naive under-forecast by 17.3% (WAPE rewards forecasting the median, which for intermittent demand is often zero). That left 21 series with a zero forecast for all 12 weeks and those series at 65% fill rate. The only choice that changes is intermittent, from naive to lightgbm (WAPE 0.746, bias -11.9%); every other pattern keeps its model.
Numbers, before and after (from rerunning the stages; earlier phase entries keep the numbers of their own run):
- Series by forecast model: lightgbm 389 and naive 61, now lightgbm 450. Series with a zero 12-week forecast: 21, now 0.
- Baseline fill rate 0.924, now 0.937 (A 0.937 to 0.952, B 0.900 to 0.908, C 0.877 to 0.895). Lost sales value 201,771, now 124,909 (down 38%), with average inventory value 140,206, now 140,441, almost unchanged.
- Fair share 0.938, now 0.952; it still beats the LP. Lead time shock, policy not updated / updated: 0.804 / 0.883 (was 0.794 / 0.865). Supplier disruption 0.860 (was 0.845).
- Total classic safety stock 58,608, now 59,231 units.
- Exceptions: 288 on 230 series (was 310 on 226). Overstock flags 23, now 0 (they were the zero-forecast series); stockout risk value at risk 27,322, now 9,152.
- Hierarchy (fold_3): bottom-up WAPE at the total is 0.049, was 0.040, and at item-DC 0.261, was 0.258: LightGBM is slightly less accurate than naive on intermittent series in that one fold, which is the 0.2-point WAPE cost the margin accepts. Bottom-up still beats top-down at every level.

## Amendment 10: two-tier LP allocation scenario
What was built: `allocate_two_tier`, an LP in which each DC's request is split into tier 1, the units covering expected demand (order-up-to level minus safety stock minus inventory position), and tier 2, the safety-stock top-up; tier 1 units carry 10 times the normal weight (`allocation.two_tier_factor`). It runs as an extra simulation scenario, `baseline_two_tier_lp`; the spec's LP stays the default policy. The solver, the exact greedy shortcut and the rounding now accept several columns per DC, with tests for every constraint, for greedy matching the solver, and a constructed case where the plain LP gives one DC all 60 units while the two-tier LP gives 20 and 40 to cover both DCs' expected demand.
Key decision: rank units by what they protect, not only by where they go. A unit that covers next weeks' expected demand prevents a likely lost sale; a unit topping up safety stock protects against an unlikely one. The spec's single-tier objective could not tell them apart.
Why: Phase 8 found fair share beating the LP on fill rate in every class. The cause was the linear objective filling the top-weight DC's whole request, buffer included, before any other DC got a unit; the two-tier version keeps the LP's priorities but spreads cycle stock first.
Numbers (from `python run_all.py --stage simulate`, 200 runs, same demand paths for all three methods):
- Fill rate: spec LP 0.937, two-tier LP 0.945, fair share 0.952, with non-overlapping p10 to p90 bands (0.934 to 0.941, 0.941 to 0.949, 0.948 to 0.955). The two-tier LP closes about half the gap to fair share.
- Cycle service (series-weeks with no lost sales): 0.889, 0.898, 0.889; stockout weeks per series: 1.330, 1.226, 1.333. The two-tier LP is best on both: it spreads stockouts less widely, while fair share serves more units in total.
- Lost sales value: 124,909, 112,162, 101,536; average inventory value 140,441, 137,478, 134,915.
- By class, two-tier vs fair share: A 0.957 vs 0.958, B 0.923 vs 0.933, C 0.911 vs 0.944. The remaining gap is in B and C: within each tier the LP still allocates all or nothing by ABC weight, so lower classes wait. Fair share remains the better default here on fill rate and lost sales; the two-tier LP is the better choice when the measure is how many series and weeks run out.
