# Design decisions

One entry per phase. Spec amendments agreed with the author are listed at the top of `docs/BUILD_PLAN.md`; each is explained here in the phase that builds it.

## Phase 0: Setup
What was built: the project skeleton (config, error type, stage runner with placeholder stages, placeholder dashboard, README with data download steps) and a Python 3.12 virtual environment with every dependency installed.
Key decision: Python 3.12 instead of the spec's 3.11 (amendment 1); config paths resolve against the project root; a `pytest.ini` sets `pythonpath = .`.
Why: 3.11 was not installed and every dependency ships stable 3.12 wheels, including LightGBM on native Windows, so no WSL is needed. Resolving paths against the project root means `run_all.py`, the tests and the app behave the same from any working directory. Without `pythonpath = .`, pytest cannot import `src` from the `tests` folder.
Numbers: installed versions: pandas 3.0.6, numpy 2.5.4, pyarrow 26.0.0, duckdb 1.5.6, statsmodels 0.15.0, lightgbm 4.7.0, scipy 1.18.1, pyyaml 6.0.3, streamlit 1.66.0, plotly 7.1.0, pytest 9.1.1. LightGBM native `lgb.train` with a Tweedie objective runs on native Windows. `pytest -q`: 2 passed.

## Phase 1: Medallion pipeline
What was built: a DuckDB pipeline that converts the three M5 CSVs to bronze parquet, selects a 150-item FOODS_3 slice, unpivots it to 2.9 million daily rows (silver), and aggregates to one weekly row per item and DC (gold) with calendar, SNAP and price features. Quality checks raise `DataQualityError` on nulls, negative units, duplicate keys, gaps after launch, missing prices, or wrong DC and item counts.
Key decisions:
- Slice before reshaping: rank FOODS_3 items on the wide table, then unpivot only the 150 chosen items, so the long table has 2.9 million rows instead of 59.2 million (30,490 series x 1,941 days) for the whole dataset.
- Slice volume window ends at fold 1's origin (amendment 2): the top 100 items by units over t 189 to 240 (weeks 11433 to 11532), plus 50 random extras from the other 723 items with the seeded generator. Ties are broken by item_id.
- Drop the partial last week: week 11617 has only 2 of its 7 days in the sales data.
- Pre-launch weeks are kept in gold but flagged `is_launched = False`; zero weeks after launch are real zeros and stay.
- DC weekly price is the mean of the distinct store-week prices, so each store counts once regardless of how many days it has. Pre-launch rows keep their observed price (M5 has none there) and are never filled.
- Price fill order for launched rows: forward-fill, then back-fill, then the item's median price across DCs, with counts logged for each step.
Why: reshaping all 30,490 series first is what causes memory errors. Ranking items on the last 52 weeks would pick items that happened to sell well in the very weeks we test on, which inflates backtest scores (selection bias); ranking on the 52 weeks before the first test window avoids that. A partial week looks like a sales drop and would distort models, metrics and segments. Weeks before an item is stocked are not zero demand: counting them as zeros would make items look intermittent and drag forecasts down. Averaging daily rows would weight stores by days; averaging store-weeks gives each store equal weight.
Numbers (from `python run_all.py --stage pipeline`): 150 items (100 top_volume, 50 random_extra), 3 DCs, 277 weeks (t 0 to 276, weeks 11101 to 11616), 2,911,500 silver rows, 124,650 gold rows (109,368 launched, 15,282 pre-launch), dropped week 11617 (2 days), 0 never-launched series, 0 launched rows missing a price (M5 prices every store-week in which an item sells), 8,100 launched zero-sales weeks kept. Gold units per DC match the raw CSV exactly (CA 7,617,313; TX 5,878,140; WI 5,089,205). Runtime 10.3 s. A second run gives identical slice and gold files.

## Phase 2: Simulated supply parameters
What was built: per item and DC, mean weekly demand, opening stock and DC capacity; per item, lead time, weekly supplier capacity, unit price, unit cost and weekly holding cost. All supply values are simulated from the real demand history, because M5 contains sales only.
Key decisions:
- Every parameter uses the last 52 launched weeks up to `T_last` (`supply.history_weeks`, added to config so the number is not hidden in code). These parameters feed only the forward simulation after `T_last`, never a backtest, so using the latest weeks is not leakage.
- Lead time is drawn once per item (uniform 1 to 4 weeks, seeded) and shared by all three DCs, because one supplier ships the item to every DC.
- Supplier capacity is 1.10 x the item's mean weekly demand summed over DCs: about 10% headroom on average, so capacity can bind when demand spikes or several DCs reorder in the same week, which is the situation the LP allocation is for (Phase 7 measures how often it does).
- Capacities are rounded up to whole units after rounding to 9 decimals, because floating point turns 1.1 x 50 into 55.00000000000001, which a plain ceiling would push to 56. A test covers this exact case.
- DC capacity is stored as a column on `supply_params.parquet` (one value per DC, repeated per item), since the spec names only two output files.
- Opening stock uses numpy rounding (round half to even); the difference from round half up is at most one unit on a tie.
Why: a planner needs supply constraints to make allocation and safety stock meaningful, and M5 has none. Deriving them from each series' own demand keeps them realistic in scale, and the fixed seed makes every run reproducible.
Numbers (from `python run_all.py --stage supply`): 450 series, 150 items, 0 series with fewer than 52 launched weeks, 0 floored at 1 unit. Lead times: 1 week 35 items, 2 weeks 36, 3 weeks 38, 4 weeks 41. Total supplier capacity 75,013 units per week against 68,129.6 units mean weekly demand. DC capacities: CA 221,380, TX 163,794, WI 159,864 units. Total opening stock 204,395 units. Unit price median 1.97, range 0.20 to 10.84. Two runs give byte-identical files.

## Phase 3: Segmentation
What was built: ABC (revenue), XYZ (coefficient of variation) and Syntetos-Boylan demand pattern (ADI and CV squared) for every item and DC, computed by a function `segment(weekly, origin, cfg)` that sees only launched weeks up to the origin. One segment set is stored per backtest fold origin (t 240, 252, 264) plus a `final` set at `T_last` (t 276).
Key decisions:
- Segments per fold (amendment 4): each fold's LightGBM features, model selection grouping and evaluation use the segment set computed at that fold's origin; the final forecast, inventory, allocation and simulation use the `final` set. A test changes every unit and price after the origin and asserts the segments do not change.
- ABC boundary rule (amendment 3): a series is A if the cumulative revenue share before adding it is below 0.80, B if below 0.95, else C. The series that pushes the share past 80% is still one of the biggest earners, so it stays A, and the top series is always A.
- Standard deviations are population (ddof 0), so a constant series has cv 0 and a single non-zero week gives cv2 0, as the spec requires. A series with zero mean is Z and its cv is left empty.
- Window: the last 52 launched weeks up to the origin. Pre-launch weeks are excluded, so a new item is not classed intermittent just because it was not yet stocked.
Why: using segments computed from weeks after a fold's origin would leak test information into features and model choice and quietly flatter the backtest. ABC drives service levels and allocation weights; XYZ shows how hard a series is to forecast; the demand pattern decides which model family suits it (smoothing methods for smooth demand, Croston or TSB for intermittent demand).
Numbers (from `python run_all.py --stage segment`): final set: ABC A 166, B 132, C 152 series, with revenue shares 0.801, 0.149, 0.049. XYZ X 297, Y 125, Z 28. Patterns: smooth 378, erratic 7, intermittent 61, lumpy 4, inactive 0. ABC by XYZ: A 129/34/3, B 83/39/10, C 85/52/15. Pattern counts per fold: fold_1 379/15/45/11/0, fold_2 381/7/53/7/2, fold_3 369/9/66/6/0 (smooth/erratic/intermittent/lumpy/inactive). Share of series whose pattern differs from the final set: fold_1 12.7%, fold_2 7.3%, fold_3 4.7%, which is the drift the per-fold rule protects against. Erratic and lumpy groups are small (4 to 15 series), so their model choice in Phase 5 rests on few series.

## Phase 4: Forecasting models
What was built: seven forecasters behind one interface, `forecast(history, future, horizon, cfg)`, returning item_id, dc_id, t, h, model, forecast and fallback: naive, seasonal naive, 4-week moving average, Holt-Winters (with simple exponential smoothing and seasonal naive fallbacks), Croston, TSB, and LightGBM (Tweedie point models plus quantile models). Every output is clipped at 0 and never NaN: a missing or non-finite value falls back to naive and is flagged.
Key decisions:
- Direct, horizon-grouped LightGBM: three models, for h 1 to 4, 5 to 8 and 9 to 12 (`forecast.horizon_groups` in config). For the group whose largest horizon is L, every lag and rolling feature for target week t uses week t - L or earlier (lags L, L+1, L+2, L+4 and 52; rolling mean and std over 4, 8, 13 and 26 weeks of the series shifted by L). Since h <= L, t - L <= origin, so every feature is known at the origin. A test sets units equal to t and asserts no feature for any target week exceeds the origin; another passes fake future units and asserts the features do not change.
- `h` is not used as a feature, although the spec lists it. With target-relative lags, a target week's feature row is identical for every h in its group, so h carries no information a model could learn from; including it would mean replicating each training row four times for nothing. Each group's model already is the horizon-specific part.
- Future rows enter the feature panel with units set to missing, so leakage is impossible by construction rather than by care. Price at the target week is used as the planned price (known in advance); its ratio to the series' median price uses the median of history up to the origin only.
- Tweedie objective (power 1.2) for the point models: weekly item sales are counts with many zeros and a long right tail, which squared error handles badly and Tweedie models directly.
- Early stopping on the last 12 weeks before the origin, then a refit on all training rows with the best iteration, so the most recent weeks are not lost to validation. Training rows need every lag feature present, which means 52 weeks plus the lag before a series contributes.
- Quantile models (0.5, 0.9, 0.95, 0.98) are trained only for the final forecast, where safety stock and the dashboard need them; the backtest scores point forecasts, so training 12 extra models per fold would cost time for nothing. Quantiles are sorted per row so they never cross.
- Croston initialises z at the first non-zero demand and p at its 1-based position, and updates only on non-zero weeks; TSB updates the demand probability every week, so it decays toward 0 when an item stops selling. Tests check Croston on [0,0,3,0,0,3,0,0,3] gives exactly 1.0 and that TSB falls but Croston does not after 20 trailing zeros.
- Holt-Winters fits run in a pool of 6 processes with one BLAS thread each (`forecast.stat_workers`). The first attempt used one process per CPU and ran out of memory (20 CPUs x 20 OpenBLAS threads each); see the local error notes.
Why: one interface lets the backtest treat every model the same way and makes fallbacks visible. Direct models avoid the error build-up of feeding forecasts back in as lags, and the lag rule makes leakage-freedom something a test can prove.
Numbers (Phase 4 acceptance check from fold 1's origin, t 240, 450 series x 12 weeks = 5,400 rows per model): every model returned 5,400 rows covering all 450 series and h 1 to 12, with 0 NaN, 0 negative values and 0 fallback series. Holt-Winters used the seasonal model for 426 series and simple exponential smoothing for 24 (fewer than 104 launched weeks). LightGBM: 69,768 training rows per group, best iterations 522, 331 and 428. Runtimes: Holt-Winters 28.1 s, LightGBM 41.0 s, the others under 0.2 s. This is a single-fold check; the scored comparison is Phase 5.

## Phase 5: Backtesting and model selection
What was built: a rolling-origin backtest over three non-overlapping 12-week folds (origins t 240, 252 and 264), in which every model trains only on weeks up to the origin, plus volume-weighted scoring (WAPE, bias, mean MASE, FVA vs naive) by model, demand pattern and ABC class, a model choice per pattern, and the residuals of each series' chosen model for safety stock and simulation.
Key decisions:
- WAPE over MAPE: MAPE divides by each week's actual, so it explodes or is undefined on the many zero and low-sales weeks in this data, and it treats an error on a 2-unit item like one on a 2,000-unit item. WAPE weights errors by volume, which is what drives stock and cost.
- Volume-weighted aggregation: WAPE and bias are computed on pooled absolute errors and pooled actuals, never as an average of per-series WAPEs, so small noisy series cannot dominate the score. A test shows the two give different answers.
- FVA vs naive: forecast value added is the naive WAPE minus the model WAPE in percentage points. If a model cannot beat "same as last week" it is not adding value, however sophisticated it is.
- Patterns per fold (amendment 4): each forecast row is grouped by the series' pattern in its own fold's segment set, so a series can count as smooth in one fold and intermittent in another.
- Model selection per pattern, not per item: with only 3 folds of 12 weeks, choosing a model per series would mostly pick whichever model got lucky on that series' noise (overfitting the backtest). Pooling all series with the same pattern gives hundreds of series-folds per choice for the main patterns.
- The selection rule was applied exactly as specified (lowest pooled WAPE, tie-break by absolute bias, inactive always TSB), even where the result is debatable (see below), so it can be explained without hand-tuning.
- Residuals for safety stock and simulation are actual minus forecast of the model each series will use in the final forecast, which is the model chosen for its final-set pattern, across all three folds (450 series x 3 folds x 12 horizons).
Why: honest out-of-sample numbers are the only defensible basis for choosing models, setting safety stock from forecast error and claiming value added.
Numbers (from `python run_all.py --stage backtest`, runtime 128.3 s): overall WAPE: lightgbm 0.280 (bias -5.8%, mean MASE 0.619, FVA +8.9 pp), tsb 0.333, croston 0.345, moving_average_4 0.348, holt_winters 0.365, naive 0.369, seasonal_naive 0.382 (FVA -1.3 pp). LightGBM WAPE per fold 0.275, 0.307, 0.261 against naive 0.458, 0.378, 0.278. By ABC, LightGBM WAPE is A 0.239, B 0.337, C 0.418. Selected models: smooth lightgbm (WAPE 0.242, 1,129 series-folds, 4.3 pp ahead of tsb); erratic lightgbm (0.547, 31 series-folds, 21.4 pp ahead of seasonal_naive); intermittent naive (0.744, 164 series-folds, only 0.2 pp ahead of lightgbm 0.746); lumpy lightgbm (0.913, 24 series-folds); inactive tsb by rule (2 series-folds; croston scored lower there, a sample too small to override the rule). 0 fallback rows in 113,400 forecasts.
Caveat on intermittent: naive wins by 0.2 pp with a -17.3% bias. For intermittent series naive forecasts zero in 49.4% of weeks while only 36.7% of actual weeks are zero. WAPE is minimised by forecasting the median, which for intermittent demand is often zero, so it rewards under-forecasting. The rule picks naive; safety stock from the larger residuals has to cover the gap, and the simulation in Phase 8 will show whether service suffers for these series. A selection rule that prefers the lower absolute bias within a small WAPE margin would pick lightgbm here; that would be a change to the agreed rule, so it is noted rather than made.
